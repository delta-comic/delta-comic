# dev 插件安装与重载重构计划

## 问题定位

2026-11-23，桌面端安装 `jmcomic` 时，目录从 `plugin-staging/<id>-<token>` 重命名到 `plugin/<id>` 失败。检查工作区时，`.temp/plugin-staging` 存在，`.temp/plugin` 缺失。在独立临时目录按同样顺序创建 staging 并执行 rename，得到 errno 2；创建目标父目录后，同一次 rename 成功。该验证覆盖文件系统行为，桌面应用中的完整安装留到实施阶段验收。

| 当前实现 | 对开发插件的影响 |
| --- | --- |
| `packages/plugin/install/lib/source.ts` 用带空文件集合的 package 表示 dev 来源，`service.ts` 用空 Map 调用文件替换 | 首装、重复安装和卸载都可能执行无意义的文件事务。现有内存测试甚至要求清空文件，无法覆盖首次创建原生目录。 |
| `packages/plugin/core/lib/adapters/fileStore.ts` 创建 staging 后直接 rename 到 live | 所有需要落盘的来源在首次安装时都可能遇到同一错误。 |
| resolver 预取 manifest、入口和 CSS，reader 随后 import 入口并再次请求 CSS | 一次安装存在重复请求，预检和实际加载可能跨越两次代码修改。 |
| `packages/plugin/vite/lib/dev.ts` 用 Vite HMR 派发函数更新，并直接更新宿主的 style；core 收到函数后仍会先调用 reader | 一次热更新有两条入口加载路径。CSS 的创建、更新和销毁跨越两个包。 |
| `packages/plugin/core/lib/composition.ts` 在启动或重载失败时进入全局安全模式，先卸载再加载；安装事务只回滚文件和数据库 | 开发服务器离线或代码编译失败可能连带卸载其他插件。记录回滚后，原先运行的插件也可能没有恢复。 |

## 实施顺序

### 1. 单独修复全新数据目录的归档安装

在 Tauri 文件后端提交 staging 前递归创建 live 的父目录。用全新临时数据根执行首次安装，随后覆盖已有版本并注入 rename 失败，检查旧文件仍可读。独立交付这一修复，以便普通插件安装也能受益。

### 2. 在安装器中显式表示开发服务器来源

由 `@delta-comic/plugin-install` 定义可辨识联合。归档分支提供待解码文件，开发分支提供已校验的 manifest 和 `dev:<port>` 来源。让类型约束每个分支的必需字段。统一保留来源匹配、保留 ID 校验、启用状态、配置和安装记录。持久化优先沿用现有 `loaderName`、`installInput` 和 `meta`，在读取边界识别已有 dev 记录。解析、端口校验和 localhost URL 构造继续使用现有 dev 协议工具。

| 操作 | 文件与运行时处理 |
| --- | --- |
| 首装 dev、dev 更新、卸载 dev | 只变更安装记录和对应运行实例。入口、样式和图标从开发服务器读取。旧实现留下的空目录允许存在，不作为已安装的依据。 |
| ZIP 切换为同 ID 的 dev | 保留旧文件到新来源激活成功，再提交清理。任何失败恢复旧记录及其启用状态，原先运行的版本应能继续使用。 |
| dev 切换为同 ID 的 ZIP | 暂存并验证新包，提交成功后释放开发会话；失败回滚暂存和记录。原服务器若已离线，显示可重连状态。 |
| 同一端口换成不同 ID 的插件 | 对已有记录执行更新或重连时核对 ID，报告冲突；从安装页显式新增时按新 ID 处理。 |

让文件删除具备与替换相同的提交、回滚语义。禁用状态下的更新只验证并写入来源，不擅自激活。将现有内存测试改为分别断言首次 dev 安装零次文件操作、来源切换带来的清理和失败恢复。

### 3. 统一首次加载、热更新与重连

resolver 负责获取并校验 manifest；reader 依据 manifest 真实导入入口并读取可选 CSS。将缺少 CSS 的 404 与入口编译、网络、导出结构错误分别报告。图标复用相同的来源地址。沿用现有 Vite HMR 和宿主管理队列，给 dev 更新绑定当前插件 ID、来源和会话代次，排队后再次检查。停用、卸载、切换来源后丢弃旧事件和迟到的请求结果。

宿主统一管理 Cordis 作用域和 style 的创建与销毁。有合法函数的 HMR 更新直接使用新函数；仅 CSS 变化时只更新当前会话的样式，包括初始 CSS 为空的情况。完整重连时重新获取 manifest、核对 ID 并导入入口。先准备新模块，再切换作用域。切换期间如激活失败，用最近一次成功加载的模块及配置重新挂载；恢复也失败时清理当前插件的注册项并显示故障状态。

### 4. 将开发服务器故障限制到当前插件

启动时区分 dev 连接失败、入口加载失败、Cordis 组件激活失败和宿主本身故障。dev 安装记录保存来源和启用意图，离线时允许其他插件继续启动。同步调整启动循环、全局 fiber 状态监听与稳定化等待，避免同一失败从另一条路径触发全局清理。插件管理页显示实际端口、失败阶段和重连操作，仅为有本地安装目录的插件提供“打开目录”。重连复用同一条加载路径。

## 验收

1. **原生文件事务**：在隔离的桌面数据根分别以 ZIP 和 dev 作为第一个插件。ZIP 首装、覆盖和失败回滚成功；dev 首装、更新和卸载不会创建该插件的 live、staging 或 backup 目录。覆盖同 ID 双向切换、旧 dev 记录和禁用记录。
2. **真实开发循环**：用同一份测试插件启动 Vite 开发服务器，经 Web 和桌面宿主的安装页输入实际的 `dev:<port>`。确认真实入口运行、图标可读、样式生效。连续修改 JS 和 CSS，检查行为更新、样式节点唯一、旧菜单或服务注册已释放。
3. **故障与恢复**：与一个普通插件同时启用，分别模拟服务器停止、入口导出错误、组件激活异常、端口被另一插件复用。重启宿主后普通插件仍可使用；恢复原服务器后通过重连恢复 dev 插件。卸载或切换后到达的 HMR 事件不能重新激活旧实例。
4. **交付记录**：用 `vp` 运行相关包测试、依赖构建和应用类型检查。分别记录 Web 与桌面实测的端口、宿主、安装结果和热更新结果。移动端的 localhost 指向设备自身，若验证移动端，应另行记录使用的端口转发环境和结果。
